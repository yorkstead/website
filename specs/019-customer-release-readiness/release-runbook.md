# Release runbook — planning only

CC-011 supplies no activation switch. Never treat an acknowledgment or globally approved review as permission to onboard a customer. Production auth/enrollment/project reads remain disabled. Do not send any invitation, email proof or recovery message in this milestone.

1. Platform engineer verifies exact code commit, all migration checksums, deployment identity and nonsecret reviewed configuration identity. Independently qualify production secrets/least privilege/TLS/cookies/security headers/cache behavior through a separately authorized adapter. Successful deployment alone is insufficient.
2. Security reviewer validates exact-release owner/customer separation, tenant denial, stale publication invalidation, secret-free logs and fail-closed routes/CSRF/rate limits. Record current technical evidence separately from owner attestation.
3. Email operator independently verifies authenticated sender/domain, SPF/DKIM/DMARC alignment, provider availability, quotas and retry/idempotency semantics. Invitation transport must not expose verifier/token in logs/URLs/analytics; proof is a separate recipient-bound credential. Qualify bounced/complained/suppressed recipients and delivery failure handling. No live provider is wired here.
4. Recovery/incident owner validates reset/session revocation, lost-mailbox identity verification, incident escalation, alerts/on-call ownership, backup restore rehearsal and rollback. Existing public reset/signup routes remain unavailable; lost-email cases need a separately reviewed identity-proof procedure, never owner impersonation or fabricated verification.
5. Owner separately reviews each fictional/approved pilot customer's tenant, explicit project mapping, verified identity, membership/view grants and current approved safe publication. Global approval never removes these blockers or creates access.
6. Owner requests a separately reviewed release/activation change bound to the qualified release and current evidence. This change must explicitly authorize each capability and pilot; CC-011 approval cannot execute it.
7. Separately authorize a limited synthetic/approved pilot, monitored rollout and stop conditions. No automatic invitation issuance/delivery/provisioning/publication.
8. Monitor tenant denials, provider failures/bounces, proof replay/rate-limit saturation, unexpected 2xx customer routes, leakage/caching, stale approvals and source invalidation. Escalation roles must be named and tested before rollout.
9. Stop on any mandatory unknown/failure/staleness, cross-tenant result, unexpected feature activation, credential/log leak, provider/auth incident, failed restore/rollback or absent incident owner. Freeze rollout and preserve evidence. Acknowledge cannot bypass stop.

Rollback summary: stop future rollout/delivery; under a separately authorized operational change restore deny-by-default customer gates, revoke affected invitation/grant/membership scope through reviewed services and consider provider session invalidation. Source changes already invalidate publication; session cookies alone do not retain authorization after lifecycle revocation. Do not delete audit/history or restore revoked access from backups. Revert UI/transport before persistence; retain additive 0016. Schema rollback/destructive restore, production migrations and config edits require separate review. Validate isolation/negative routes and recovery before proposing resumption.

Evidence expires no later than its catalog TTL; any release commit, schema/checksum identity, relevant configuration identity, adapter observation or required evidence change invalidates review. Renew/review exact evidence, never copy an old approval to a new release.
