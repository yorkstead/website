# Threat model

- Tenant selectors and project IDs are hostile. Customer API accepts headers and project selector only; verified isolated provider subject determines scope. Rejoin all lifecycle tables within the data SELECT to close authorization/query gaps.
- Owner identity is resolved by existing owner session verifier, never actor headers. Trusted dependency injection is test-only infrastructure, not an exported action. Every transition verifies owner and records actor/time through database triggers.
- Over-disclosure: strict schemas plus field-by-field source extraction and adapter construction; customer queries exclude source digests, owner actors, audit, unapproved payloads and workspace JSON. Descriptions/Update content require explicit selection and human review; allowlists cannot semantically detect sensitive prose.
- Stale approval: locked persisted source, digest comparison, CAS revision and atomic database invalidation on source update/delete. Full-workspace invalidation is intentionally conservative. Browser-local unsaved data is outside the server trust boundary.
- Concurrency: workspace lock precedes active tenant/mapping locks and publication row lock. Conflicting actions at one revision produce one winner; source edits serialize against approval. Active lifecycle joins are repeated in one projection query. Requests already executing can observe their statement snapshot; later reads observe committed revocation.
- Audit tampering: triggers prohibit snapshot deletion and audit update/delete/truncate; verified service actor and decision timestamp are generated server-side. Database administrator and code execution compromise remain outside the application boundary; transaction settings are not credentials and must never be exposed through arbitrary SQL APIs.
- Availability: workspace saves invalidate all prepared records; this may cause extra review but never automatic publication. Source/mapping absence fails closed. No cross-customer fallback, no external route, no customer caching.
