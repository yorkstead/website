# Threat model
- Invitation theft: possession only initiates delivery to the stored recipient; an independent random email proof is required. No typed recipient overrides.
- Account takeover: existing credential hashes never overwritten; unverified preexisting accounts fail closed and require separately reviewed recovery. Existing verified users must sign in with their password.
- Forged verification/replay: SHA-256 verifiers of high-entropy secrets, ten-minute expiry, invitation binding, row locks, atomic consumption. No boolean verification input or production test adapter.
- CSRF/session fixation: same configured origin required for JSON mutations; provider creates fresh isolated sessions. No arbitrary callback URLs; sign-out uses actual provider revocation.
- Leakage: invitation/proof fields only in POST bodies and transient form memory; no URL query, persistent storage, analytics, audit payload or exception echo. Pages/API use no-referrer and no-store.
- Abuse: database-shared limits for operation and recipient/invitation keys; no trust in arbitrary forwarded IP headers. Global operation limit intentionally trades availability for safe bounded load.
- Cross-tenant access: reuse full active identity/tenant/membership/project/grant join each request; synthetic data only, no unscoped real-data query.
- Partial failure: account/proof/identity transaction atomic; subsequent authentication/redemption can be retried with existing password. No access exists before CC-006 completes. Delivery failure invalidates the challenge and never reports proof success.
- Concurrency: tenant then invitation locks match CC-006; recipient advisory lock prevents duplicate first accounts across invitations. Single proof consumer wins. Revocation after proof is still enforced at redemption.

## Review findings and mitigations
- React streaming can turn a late `notFound()` into HTTP 200. A narrowly matched Next proxy now denies disabled customer pages and endpoints before rendering; server components/handlers retain independent checks. Owner/public paths are outside the matcher.
- Bound JSON bodies to 4096 bytes while streaming before parsing; reject cross-site, missing/wrong origin and non-JSON mutation requests before database work.
- Database connection setup has a ten-second timeout and enrollment runtime queries a fifteen-second timeout; preserve TLS verification through the existing URL helper.
- Distributed rate limiting intentionally includes operation-wide limits to avoid trusting arbitrary client IP headers. Production activation requires reviewing expected traffic/capacity and retention cleanup for expired challenge and rate-limit rows. This is an availability/release concern; no current production exposure exists.
- Account creation uses a narrowly scoped transactional repository write with Better Auth's configured password hasher after independent email proof. It does not enable Better Auth signup or relax either provider hook. An identity without membership/grants is not portal authority. Tests prove intermediate state has no project grant and can resume through actual sign-in/redemption.

## Rate-limit capacity and operations
The current PostgreSQL-backed limits are shared by all application instances connected to the same database. They are fixed windows anchored at the first attempt, resetting on the first attempt after fifteen minutes; they are not sliding windows or requests-per-second limits.

| Bucket | Current limit | Capacity and interaction |
| --- | --- | --- |
| Operation-wide (`begin`, `complete`, `sign-in`, `sign-out`, `redeem`, `recovery` separately) | 100 attempts per 15 minutes per operation | Shared across every customer, tenant and instance. About 6.7 attempts/minute averaged over a window, but up to 100 can arrive as a burst. |
| Invitation and operation (`begin`, `complete`, `redeem` separately) | 10 attempts per 15 minutes | Bound to the token digest; different operations have independent counters. |
| Normalized sign-in email | 10 attempts per 15 minutes | Shared between direct sign-in and authentication following completed email proof. This also prevents an existing account from obtaining extra password attempts through enrollment. |
| Delivery recipient | At most one challenge initiation per minute | Uses a transaction/advisory lock and recent challenge rows across invitations for the same stored recipient; failed delivery also consumes this cooldown. Operation/invitation limits still apply. |

Rejected counted attempts increment their buckets. The operation-wide counter is charged before parsing, so malformed same-origin JSON requests consume shared capacity. Origin/content-type failures are rejected before database work. There is no trusted client-IP key: arbitrary forwarded headers cannot grant extra capacity. An attacker can exhaust a shared operation bucket and deny legitimate requests, including sign-out requests until that operation window resets. Existing sessions must still be revoked through a reviewed support procedure if normal sign-out is unavailable. Fixed windows also permit boundary bursts. These limits are conservative test-foundation defaults, not an approved production traffic budget.

Each accepted mutation performs a shared counter upsert, with extra per-invitation/email upserts as applicable. Hot operation rows serialize under load and database pool/lock waits can become the bottleneck before a request is rejected. Email delivery and password hashing add separate latency/cost; the cap is not a concurrency limit, edge flood defense or guaranteed throughput. Monitor sanitized operation outcome counts, rejection ratios, database latency/lock waits, pool saturation and delivery failures. Do not log addresses, raw tokens, proof values, passwords or session secrets. Current generic failures do not expose bucket state; telemetry/alerting and a support runbook require separate review before activation.

Storage/database errors fail closed through the generic controller error path; there is no in-memory fallback that could reset limits across replicas. Rate-limit rows and expired/consumed challenges currently have no automatic cleanup. Before release, define retention, indexed bounded cleanup and capacity/load tests against expected tenant/customer volume. Cleanup must not delete live rate windows or unexpired usable challenges, which would reset defenses or break recoverability. Do not clear counters as a routine response to abuse, and do not raise limits or trust IP headers without review. Suspected sustained abuse calls for keeping customer activation closed (production is already hard-disabled), inspecting sanitized metrics and the database, and reviewing edge protections and fairness before reopening. Production release requires an approved capacity budget, burst/concurrency safeguards, monitoring/alerts and retention/support ownership; no such activation is authorized by these corrections.
