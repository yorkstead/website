# Disabled operations and future qualification

CC-012 installs no dispatch worker, scheduling hook, recovery HTTP handler, sending endpoint, production keyring or provider configuration. Customer Communications is read-only in every environment. `/api/customer-communications/webhook` returns 404 before parsing or dependency access. Existing contact-inquiry notifications/webhook remain outside this customer subsystem and unchanged.

## Isolated reproduction

Use disposable PostgreSQL 16, apply/repeat migrations through the normal runner, and set identical plain-loopback `DATABASE_URL` and `TEST_DATABASE_URL` with a `test`/`disposable` database name. `CUSTOMER_COMMUNICATIONS_DISPOSABLE=enabled` is required by trusted queue/recovery/event constructors outside production. No production flag can authorize them. Construct the deterministic fake and a randomly generated in-memory AES-256 keyring; never use real recipient addresses or provider credentials. No fixture endpoint or mailbox is shipped in Next.

`bun test` covers services directly. `bunx playwright test -c playwright.cc012.config.ts` uses the actual existing owner Better Auth and read-only application API at mobile/desktop widths. Run database tests before browser fixtures or use independent databases: the historical lead-conversion test assumes no pre-existing `primary` workspace. Browser owner setup deliberately leaves a fictional persisted workspace. Do not run stateful database and owner-browser fixtures simultaneously against one database.

## Delivery semantics

The authoritative CC-006 preparation/issuance/redemption lifecycle remains distinct from queue delivery. Optional transaction hooks append intent/custody only after existing authorization and validation. Queue failures roll back the action. Provider transient/permanent failures never revoke invitations or create grants. Every dispatch rechecks tenant, invitation, all invited projects, exact recipient, proof/recovery state and any known identity suspension. Queue jobs retain immutable scope and fixed template version. Version 1 copy/URL construction must stay immutable during retries; future template changes need a new version/explicit migration strategy.

Claim lease: 30 seconds; transport timeout: at most 5 seconds with AbortSignal and Promise race; maximum five claims/transmission attempts, exponential backoff capped at 60 seconds plus up to one second jitter. Stale-lease recovery uses a new random fencing token; stale completions cannot update job state. Short-lived ciphertext is authenticated to job/key version and expires at the earlier authoritative action expiry or 590 seconds. Missing, expired, tampered or retired-key custody cancels delivery. Terminal completion deletes custody. No token is regenerated for a retry.

There is an unavoidable uncertainty window after provider acceptance and before database commit. Retry uses the same idempotency key, fixed recipient, template and token, always within the documented provider 24-hour idempotency window. This bounds duplicate mail but does not promise exactly-once transport or receipt. Revocation committed before the dispatch authority lock suppresses delivery; an already accepted/in-flight message cannot be recalled, and its action is still denied by authoritative redemption checks. Independent proof remains required; email acceptance/delivery never changes verification, tenant membership or project grants.

Production recovery remains blocked. The disposable service updates one existing `customer_auth.account` credential with the configured Better Auth hasher and deletes all subject sessions atomically with challenge consumption; no passwordless conversion/account creation. It rechecks verified provider email, active identity, tenant and membership. Begin returns the same message for unknown, unsupported, throttled, suppressed and infrastructure-failure cases. Limits are shared database buckets: five requests per normalized account and twenty per trusted network source per fifteen minutes; completion ten per challenge and thirty per source. The future HTTP adapter must obtain a canonical source from a reviewed trusted proxy boundary; never accept a browser-supplied source or arbitrary forwarded header. No lost-mailbox bypass or automatic grant repair exists.

## Resend documentation verified during implementation

- [Raw-body webhook verification](https://resend.com/docs/webhooks/verify-webhooks-requests): installed Resend SDK verifies Svix `svix-id`, `svix-timestamp`, `svix-signature`. Local fixtures sign `id.timestamp.rawBody`; invalid/modified/stale/future requests fail.
- [Bounce event reference](https://resend.com/docs/webhooks/emails/bounced): event `email.bounced`, `data.email_id`, `data.bounce.type` of `Permanent` drives hard suppression. Other bounce classifications remain delayed and never imply verified delivery.
- [Idempotency keys](https://resend.com/docs/dashboard/emails/idempotency-keys): same-key retries, 24-hour retention; bounded custody/retries remain inside it.
- [Send endpoint](https://resend.com/docs/api-reference/emails/send-email): fixed `/emails` transport and `Idempotency-Key`; no attachments, arbitrary headers, caller HTML or redirects. Adapter is hard-disabled before transport/key use in CC-012.

Webhook processing persists only signed event ID, scoped job ID, allowlisted event and timestamps. Unknown event types are ignored after verification; unknown message IDs return retryable failure so an event preceding acceptance persistence is not lost. Delivery precedence is accepted < delayed < delivered < failed < bounced < complained; terminal adverse evidence cannot be overwritten by late acceptance/delivery. Provider accepted job state and provider delivery observation are separate. Complaints/permanent bounces create digest-only suppression for future enqueue/dispatch. Events/audit are append-only.

## Separately authorized activation checklist

Independently qualify sender ownership and approved From address, SPF/DKIM/DMARC, provider account/key restrictions, exact-environment webhook signing, rate/capacity/timeout behavior, idempotency retention, and bounce/complaint response. Establish least-privilege queue/custody DB roles, encrypted storage backups/retention, cleanup/monitoring, key custody/rotation and outage response. Keyring rotation retains the previous key only through the maximum ten-minute custody window, then retires it; stranded jobs cancel rather than regenerate credentials. Webhook rotation permits at most current plus explicitly configured previous secret, with a reviewed overlap/retirement schedule. No production secret provisioning occurs here.

Qualify Better Auth password/session/cache behavior and lost-mailbox assisted verification. Wire reviewed customer fragment consumers and trusted controllers only under a separate activation change; the existing customer forms/routes remain unchanged and disabled in production. Global/provider code existence and fake tests cannot qualify these controls. Independent exact-release technical evidence and per-customer authorization are still mandatory, and launchReady remains false.

Rollback application adapters/UI first and keep deny gates closed; retain additive schema, old manifests, immutable intent/evidence/audit and historical reviews. Never remove historical migrations or reactivate/reissue failed actions automatically. No manual production migration/deployment or merge is authorized.
