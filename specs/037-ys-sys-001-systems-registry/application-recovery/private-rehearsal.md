# Private Production-derived application rehearsal

The executable entry point is `scripts/recovery/run-private-rehearsal.sh`. This implementation is **not yet demonstrated against Docker in the engineering environment** and does not itself authorize a Production-derived run. Run it only after separate owner approval. The archive, decrypted copy, connection values, synthetic passwords, browser output, and all data-derived evidence must stay on the owner's private ThinkPad WSL environment.

The target setup and runtime verification scripts are exercised against a synthetic PostgreSQL 18.6 service in CI. This verifies role setup, normal Better Auth credential sign-in, runtime RLS visibility, and denied privileges with synthetic rows only. The orchestrator adds the target/restore/app/proxy/browser lifecycle; a successful private run must still be separately reviewed. Synthetic CI is not a Production-derived rehearsal.

## Owner invocation

1. On ThinkPad WSL, create an owner-controlled directory on the approved private local storage and set it to mode `0700`. Create a separate mode-`0600` shell configuration file inside it. Set these variables in that file: `YS_PRIVATE_DOCKER_CONTEXT`, `YS_PRIVATE_WORKSPACE_ROOT`, `YS_PRIVATE_ARTIFACT`, `YS_PRIVATE_ARTIFACT_SHA256`, `YS_PRIVATE_ARTIFACT_FORMAT=custom`, `YS_PRIVATE_AGE_IDENTITY`, `YS_PRIVATE_POSTGRES_IMAGE` (local PostgreSQL 18.6 image pinned by digest), `YS_PRIVATE_NGINX_IMAGE` (local nginx Alpine image pinned by digest), `YS_PRIVATE_APP_REPOSITORY`, `YS_PRIVATE_APP_REVISION=6fba1dd297067f7c3af219d2ffdec18006274c53`, and `YS_PRIVATE_OWNER_CONFIRM='YS-SYS-001 APPROVE PRIVATE DISPOSABLE REHEARSAL'`. Keep the file and values local. The app repository must already contain the pinned commit; both pinned container images must already be available locally. Do not add secrets or fingerprints to GitHub, CI, chat, or public artifacts.
2. Verify the configuration is a trusted owner-authored file with mode `0600`, then run `bash scripts/recovery/run-private-rehearsal.sh /private/path/rehearsal.env`. T0 is recorded before the script hashes, decrypts, or restores the artifact. The script prints only the generated target ID and private workspace path; its sanitized report stays in that workspace.
3. The script performs the normalized custom-format restore, target preparation and privilege probes, pinned image builds, startup, internal TLS/browser checks, business-data fingerprint comparison, egress denial check, T-ready, target-scoped teardown, original-artifact identity verification, and separate T-cleanup-verified recording. It does not apply migrations.
4. For uncatchable host shutdown, read the target ID from the known private workspace marker, re-source the same trusted config, then run the scoped recovery command below. It validates the configured Docker context, every resource's target label and exact target name/tag, verifies no target resource remains, checks the original artifact identity, and removes only the workspace's plaintext/secrets/TLS and extracted application-source directories. It retains diagnostics:

   ```bash
   TARGET_ID=$(cat "$PRIVATE_WORKSPACE/.ys-sys-001-target-id")
   python3 scripts/recovery/private-rehearsal-cleanup.py cleanup \
     --target-id "$TARGET_ID" --workspace "$PRIVATE_WORKSPACE" \
     --artifact "$YS_PRIVATE_ARTIFACT" --docker-context "$YS_PRIVATE_DOCKER_CONTEXT"
   ```

   If cleanup cannot positively identify every target resource or the context has changed, it removes nothing. Resolve the mismatch locally; never use Docker prune. Synthetic fault injection is accepted only when `YS_PRIVATE_SYNTHETIC_FIXTURE=true` and the encrypted fixture filename begins `ys-sys-001-synthetic-`; stages are `restore`, `preparation`, `application-startup`, `browser`, `integrity`, `interrupt-int`, `interrupt-term`, and `cleanup`. The injected cleanup-failure case deliberately leaves its labeled resources for the scoped recovery command.

## Reconciled authentication and routine findings

The owner-reported target contains existing authentication users, so `/api/auth/sign-up/email` intentionally rejects registration once any user exists. Do not delete, edit, or repurpose a restored identity. `scripts/recovery/prepare-private-rehearsal.ts` seeds one new `owner@recovery.test` user and credential account with Better Auth's own configured password hasher, using the separate target setup connection. The browser then uses the ordinary `/api/auth/sign-in/email` endpoint and `/api/auth/owner-session-status`; the test never calls registration. A collision with the reserved synthetic email aborts without modifying the existing row.

Migrations `0011`, `0012`, `0014`–`0018`, and `0020` define the reported 37 application routines through migration `0022`: 34 trigger functions, two trigger-called helpers (`document_require_actor` and `inquiry_retirement_digest`), and `retire_inquiry`. The 34 trigger functions attach to migration-defined document, invitation, publication, access, readiness, communications, inquiry-retirement, and legacy-directory tables. They enforce invariants, reject unauthorized or immutable changes, and in write paths create local audit/history or revision rows. `document_require_actor` validates transaction-local actor/role settings; `inquiry_retirement_digest` reads an inquiry to compute a digest; `retire_inquiry` locks and writes inquiry-retirement records and is explicitly revoked from PUBLIC by migration `0018`. Review found no dynamic SQL, `SECURITY DEFINER`, network/file/process calls, or other external side-effect primitives in these 37 migration definitions. None is called by approved owner sign-in, owner session check, dashboard/workspace GET, legacy Directory GET, or tenant-authorization SELECT paths. Preparation checks exact target routine bodies and trigger attachments, revokes PUBLIC routine execution in the disposable target, and gives runtime no application-routine EXECUTE. Runtime verification also calls the reviewed read-only `document_require_actor` helper and requires PostgreSQL's direct EXECUTE permission-denial error. PostgreSQL trigger invocation remains intact; application runtime has no business-table writes that could activate those triggers.

These are repository-source findings plus owner-reported catalog metadata, not an independent inspection of the private restore. Owner execution must still prove the fresh target has the expected 37 definitions and trigger inventory. If it does not, stop and report only aggregate mismatch counts; do not broaden routine access.

## Runtime privilege boundary

Preparation creates a different `NOINHERIT` non-superuser runtime login with no role memberships, CREATE, TEMPORARY, database/role administration, ownership, sequence access, or application routine EXECUTE. It revokes database CREATE/TEMPORARY, PUBLIC table/sequence grants, and PUBLIC EXECUTE on application routines in the disposable target only. It enables target-only RLS on the three Better Auth relations and five tenant-authorization relations, with nine runtime-specific policies limiting visibility to the generated synthetic owner and target fixtures. Existing target policies or RLS flags on these relations cause a fail-closed stop. The setup role remains their owner; runtime has neither ownership nor `BYPASSRLS`. It grants:

| Category | Runtime grant |
|---|---|
| Database | CONNECT only; no CREATE or TEMPORARY |
| Schemas | USAGE on `public`; no access to `customer_auth` |
| SELECT | `application_migrations`, `workspaces`, `workspace_snapshots`, `system_directory_entries`, `contact_inquiries`, `inquiry_retirements`, `crm_proposals`, `conversion_events`, `research_opportunities`, owner-auth `user`, `account`, `session`, and five synthetic tenant authorization relations |
| INSERT | `public.session` only, for normal owner sign-in session creation |
| UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER | None |
| Sequences | None; current approved paths use text IDs and need no sequence |
| Application routines | None; required read/auth paths invoke no user-defined routine |

The setup role inserts a new synthetic owner/account, two uniquely named tenant/identity/membership/project/grant fixtures, and one synthetic hidden-row control set. It does not modify restored rows. RLS must expose exactly the owner/account, the two target-scoped fixture sets, and the sign-in session to runtime; the hidden controls and all restored identity/mapping rows must remain invisible. Those synthetic fixtures and database-generated audit effects exist only in the disposable target, which must be destroyed after testing. The runtime performs no business-data DML. Existing Production-derived identities and records remain unchanged.

The approved tenant test calls the application's `getCustomerProjectAccess` authorization query as the runtime role: each synthetic subject must see its own synthetic project, and must receive no access to the other tenant's project. This proves application-layer tenant scoping. The owner-reported restored source has zero RLS policies. The rehearsal deliberately adds target-only RLS as a runtime identity privacy boundary; this is a normalized security control and is not evidence of source-to-target RLS equivalence. Restoring with `--no-owner --no-acl`, making the setup role owner, revoking broad grants, and adding runtime RLS can establish application functionality on a deliberately normalized target. It cannot establish faithful source-to-target ownership, ACL, membership, or RLS recovery.

## Clock and cleanup

- **T0:** the orchestrator records UTC and monotonic start time before it reads the artifact or age identity. Recovery time is continuous; no wait is paused or excluded.
- **T-ready:** the orchestrator records UTC and monotonic time only after restore, app startup, owner sign-in/authorization, rendered dashboard, Directory read, tenant isolation, integrity, and network/side-effect checks pass. `T-ready - T0` must be at most 60 minutes.
- **T-cleanup-verified:** after all target resources are absent, ephemeral plaintext and credentials are removed, unrelated Docker resource inventory is unchanged, and the original encrypted artifact identity matches, the orchestrator records a separate UTC and monotonic cleanup timestamp. Cleanup verification is mandatory; failure makes the rehearsal FAIL even if T-ready met 60 minutes.

Cleanup must use the generated target ID and verify labels and exact resource names/tags before removal. It compares the Docker context to the explicit config value and fingerprints unrelated Docker resources before and after teardown. It verifies the encrypted artifact's device/inode/size/mtime/digest identity before removing only the workspace's `plaintext`, `secrets`, `tls`, and extracted `app-source` directories; diagnostics and the sanitized report remain private. Never use broad Docker prune commands. T-ready and T-cleanup-verified are separate sanitized fields. Do not upload the report or any private artifact to GitHub, CI, or a public artifact store.
