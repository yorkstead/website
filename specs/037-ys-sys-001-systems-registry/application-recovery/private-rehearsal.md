# Private Production-derived application rehearsal

This procedure is **owner-operated and NOT RUN**. It does not authorize artifact access, decryption, restore, or rehearsal execution. The public repository contains only the procedure and code; the archive, decrypted copy, connection values, synthetic passwords, browser traces, and all data-derived evidence stay on the owner's private ThinkPad WSL environment.

## Reconciled authentication and routine findings

The owner-reported target contains existing authentication users, so `/api/auth/sign-up/email` intentionally rejects registration once any user exists. Do not delete, edit, or repurpose a restored identity. `scripts/recovery/prepare-private-rehearsal.ts` seeds one new `owner@recovery.test` user and credential account with Better Auth's own configured password hasher, using the separate target setup connection. The browser then uses the ordinary `/api/auth/sign-in/email` endpoint and `/api/auth/owner-session-status`; the test never calls registration. A collision with the reserved synthetic email aborts without modifying the existing row.

Migrations `0011`, `0012`, `0014`–`0018`, and `0020` define the reported 37 application routines through migration `0022`: 34 trigger functions, two trigger-called helpers (`document_require_actor` and `inquiry_retirement_digest`), and `retire_inquiry`. The 34 trigger functions attach to migration-defined document, invitation, publication, access, readiness, communications, inquiry-retirement, and legacy-directory tables. They enforce invariants, reject unauthorized or immutable changes, and in write paths create local audit/history or revision rows. `document_require_actor` validates transaction-local actor/role settings; `inquiry_retirement_digest` reads an inquiry to compute a digest; `retire_inquiry` locks and writes inquiry-retirement records and is explicitly revoked from PUBLIC by migration `0018`. Review found no dynamic SQL, `SECURITY DEFINER`, network/file/process calls, or other external side-effect primitives in these 37 migration definitions. None is called by approved owner sign-in, owner session check, dashboard/workspace GET, legacy Directory GET, or tenant-authorization SELECT paths. Preparation checks exact target routine bodies and trigger attachments, revokes PUBLIC routine execution in the disposable target, and gives runtime no application-routine EXECUTE. Runtime verification also calls the reviewed read-only `document_require_actor` helper and requires PostgreSQL's direct EXECUTE permission-denial error. PostgreSQL trigger invocation remains intact; application runtime has no business-table writes that could activate those triggers.

These are repository-source findings plus owner-reported catalog metadata, not an independent inspection of the private restore. Owner execution must still prove the fresh target has the expected 37 definitions and trigger inventory. If it does not, stop and report only aggregate mismatch counts; do not broaden routine access.

## Runtime privilege boundary

Preparation creates a different `NOINHERIT` non-superuser runtime login with no role memberships, CREATE, TEMPORARY, database/role administration, ownership, sequence access, or application routine EXECUTE. It revokes database CREATE/TEMPORARY, PUBLIC table/sequence grants, and PUBLIC EXECUTE on application routines in the disposable target only. It grants:

| Category | Runtime grant |
|---|---|
| Database | CONNECT only; no CREATE or TEMPORARY |
| Schemas | USAGE on `public`; no access to `customer_auth` |
| SELECT | `application_migrations`, `workspaces`, `workspace_snapshots`, `system_directory_entries`, `contact_inquiries`, `inquiry_retirements`, `crm_proposals`, `conversion_events`, `research_opportunities`, owner-auth `user`, `account`, `session`, and five synthetic tenant authorization relations |
| INSERT | `public.session` only, for normal owner sign-in session creation |
| UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER | None |
| Sequences | None; current approved paths use text IDs and need no sequence |
| Application routines | None; required read/auth paths invoke no user-defined routine |

The setup role inserts only a new synthetic owner/account and two uniquely named synthetic tenant/identity/membership/project/grant fixtures. It does not modify restored rows. Those synthetic fixture rows and their database-generated audit effects are confined to the disposable target, which is destroyed after testing. The runtime performs no business-data DML. Existing Production-derived identities and records remain unchanged.

The approved tenant test calls the application's `getCustomerProjectAccess` authorization query as the runtime role: each synthetic subject must see its own synthetic project, and must receive no access to the other tenant's project. This proves application-layer tenant scoping. The owner-reported restore has zero RLS policies, so do not claim RLS isolation.

## Clock and cleanup

- **T0:** owner declares the recovery incident and runs `python3 scripts/recovery/private-rehearsal-clock.py start --state "$PRIVATE_DIR/rto.json"` before artifact selection/decryption or any other recovery action. No pause or excluded wait time.
- **T-ready:** after restore, app startup, owner sign-in/authorization, rendered dashboard, Directory read, tenant-isolation checks, integrity comparison, and network/side-effect checks all pass, run `python3 scripts/recovery/private-rehearsal-clock.py ready --state "$PRIVATE_DIR/rto.json"`. The helper records UTC and monotonic elapsed time. RTO is `T-ready - T0` and must be at most 60 minutes.
- **T-cleanup-verified:** after stopping/removing every resource with this target label, securely removing the temporary decrypted copy and generated local secret files, verifying no target-labeled container/network/volume/image remains, and verifying the original encrypted artifact's local identity is unchanged, run `python3 scripts/recovery/private-rehearsal-clock.py cleanup-verified --state "$PRIVATE_DIR/rto.json"`. This is a separate timestamp; cleanup verification is mandatory, and any cleanup failure makes the rehearsal FAIL even if T-ready met 60 minutes.

Cleanup must use the generated target ID and verify labels before removal. Never use broad Docker prune commands. Keep T-ready and T-cleanup-verified as separate sanitized fields. Do not upload the report or any private artifact to GitHub, CI, or a public artifact store.
