# Application-recovery rehearsal plan

1. **Create isolated databases.** In a dedicated GitHub Actions job with read-only repository permission, generate synthetic PostgreSQL credentials and create separate `docker network create --internal` networks for the migration source and restored-app runtime. Start source and target PostgreSQL 18 containers with private ephemeral storage and no published database ports. Fixed host-side schema/test helpers connect to Docker-assigned container IPs only after verifying those IPs fall inside their inspected private network subnets. Do not expose either database outside the CI host.
2. **Prepare the 0022 source.** Apply only migrations `0001`–`0022` using the shared migration parser and canonical SHA-256 rules. Verify the resulting ledger. Prepare the existing Better Auth schema on this synthetic source using the repository's existing auth migration command. The migration ledger must still end at `0022`.
3. **Archive and restore.** Create a full custom-format synthetic archive in a mode-0700 temporary workspace, restore it into the new target, and delete the plaintext archive on all exits. Do not include the owner-reported Production archive or actual data.
4. **Preflight the restored target.** Compare the exact 22 checksums and run read-only aggregate checks for migration-23/24 absence, empty legacy Directory state, zero orphan audit rows, and required enabled Directory triggers.
5. **Build and start the application.** Build the production Next.js image using only synthetic build configuration. Run it as a non-root, read-only container with bounded tmpfs writable paths, attached only to the restored target and internal runtime network. The migration source is not attached to the app's network. Run a synthetic HTTPS reverse proxy for secure Better Auth cookies. Run Chromium and Playwright in a separate read-only test container on that same internal network; resolve the test hostname through Docker's network alias. Do not publish any application, database, proxy, or browser ports. Fixed host-side schema helpers connect only to Docker-assigned database IPs verified against their inspected private internal-network subnets.
6. **Prove network isolation.** Assert both Docker networks' `Internal` flags and exact membership (source alone on its network; restored target, app, proxy and Playwright browser on the runtime network). From an ephemeral probe container on the runtime network, attempt a TCP connection to a fixed public test address and require failure. Do not interpret application flags as the egress control.
7. **Exercise the app.** Use the Playwright browser container on the internal runtime network to reach the proxy by its Docker network alias. Create and sign in a synthetic owner via the existing bootstrap endpoint, verify owner-session authorization, load the dashboard and legacy Directory read API, and assert anonymous and tenant-selector requests fail closed. Keep Registry activation disabled.
8. **Test tenant isolation.** Execute the existing database-backed client project projection suite against the restored target. Its fixture creates two synthetic identities/tenants, authenticates both with Better Auth, verifies own-project reads, cross-tenant denials, and direct-header spoof rejection.
9. **Postflight and report.** Re-run the read-only schema/ledger/Directory checks. Produce an aggregate JSON report with check statuses and measured synthetic phase durations. Upload only that redacted report. Always stop/remove containers, networks, temporary archive, proxy certificate, and private workspace. No service port or host resolver entry is created.
10. **Converge.** Map each acceptance criterion to the exact CI job and sanitized report. Record skipped local Docker checks explicitly. Keep Production migrations and full RTO status `NOT RUN` / `NOT DEMONSTRATED`.
