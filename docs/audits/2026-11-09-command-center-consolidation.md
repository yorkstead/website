## 3. Confirmed duplication versus intentional integration

### Confirmed duplicated fields or manual re-entry

- **Marketing ↔ CRM sales fields:** Marketing JSON still retains its legacy stage/next-action/date values while linked. The editor hides them and reads CRM as canonical; retained legacy values restore on unlink. This is a confirmed stale shadow copy, deliberately retained for reversible unlink. Recommendation: keep this compatibility behavior for now; if removal is chosen, first inspect existing linked JSON and specify migration/rollback behavior.
- **Marketing ↔ CRM identity and value:** a linked Marketing prospect retains its own company/contact details, while CRM holds inquiry identity; Marketing activity rows can also record an `audit-paid`/`client-won` value while CRM proposal rows hold explicit amounts. This creates a structural route to duplicate contact/sale values and requires manual reconciliation, though no production rows were queried so actual duplicate identities or financial double-counts are unconfirmed. Preserve Marketing attribution/history but label its booked-revenue metric as attribution/reporting and treat accepted CRM proposal value as the commercial amount authority.
- **Marketing ↔ Opportunity Discovery account:** both independently model a business and operational signal, with no direct relationship field between them. Each can link/promote to a Website CRM inquiry, so CRM can be a shared junction, but the two upstream systems do not cross-check one another before entry. Structural overlap is confirmed; whether any company is duplicated in current data is unverified because no production records were read.
- **Consultation contact identity:** a linked consultation stores name/business/email in addition to `lead_id`; new consultations opened from CRM prefill them, but the consultation draft allows editing. This is a second identity snapshot, useful as meeting-time context but a drift risk. Recommendation: keep the snapshot for historical context; make the CRM identity visibly canonical and avoid asking the operator to re-enter it. Decide whether edits are meeting-specific snapshots or should be locked before changing behavior.
- **Sales next-action fields:** CRM `next_step`/`follow_up_at` and proposal `next_action`/`next_action_at` are both independently editable and schedulable. They belong to different record types, so they are not duplicate records, but create parallel reminders for one sales relationship. Proposal actions already appear in the dashboard sales summary and source-labeled unified attention view. Recommendation: preserve proposal-specific actions and source labels; avoid copying them into CRM follow-up fields.
- **Separate research and sales identities:** Discovery case business/contact context and a promoted CRM inquiry overlap, and promotion may create or link the CRM inquiry. This is intentional: evidence/history and research permissions remain with Discovery, while CRM owns commercial follow-up. Do not merge or delete either record automatically.
- **Marketing and Discovery may overlap on account identity:** Marketing owns founder-led outreach and campaign attribution; Discovery owns evidence-led operational problem research and commercial-permission gating. Similar company names do not establish duplicate records; linking each to CRM preserves their different purposes. No production data comparison was performed.
- **Separate task systems:** workspace tasks and Google Tasks may represent the same real-world work, but have independent IDs, completion state, and owners. This is confirmed cross-system overlap potential, not confirmed duplicate rows. Preserve their source labels and do not infer deduplication by title.
- **Hub CRM and Website CRM:** the Hub can stage leads in its own CRM review queue; Website CRM is the canonical website sales system. The UI explicitly says staging does not create a Website CRM record and that safe lead matching is not established. Treat as an intentional manual integration boundary; no automated merge is safe today.
- **Proposal content and proposal metadata:** CRM records amount/state/action metadata while the email draft action creates a `mailto:` draft from lead context. There is no evidence these are linked to a versioned proposal document. This is a manual handoff, not duplicate persistence.

### Intentional integration and boundaries to retain

- Marketing → CRM is an explicit ID relationship with canonical CRM reads and no CRM creation or field mirroring.
- Opportunity Discovery → CRM promotion requires validated evidence, interview, permission, and explicit owner confirmation; it links to an existing matching lead or creates a CRM record only after duplicate checks.
- CRM → project conversion is atomic/idempotent and preserves existing workspace/project storage.
- CRM → consultation and CRM → proposal are one-to-many record relationships that preserve their own workflow data while linking to the exact inquiry.
- Owner publishing → customer portal is a reviewed, safe projection of approved workspace source data. Client publishing/access/readiness are not redundant dashboards and must not be collapsed into an unreviewed customer route.
- Website → Hub / Google Tasks are server-side, explicitly reviewed integrations. Systems Registry and Operations remain distinct inventory/evidence and runtime-observation functions.

## 4. Incomplete, obsolete, or disconnected functionality

1. **Consultation identity can drift from CRM.** `lead_id` remains linked, but snapshot fields are editable. The create-from-lead path does prefill, so no routine re-entry is required unless the owner changes those values; the UI should make snapshot semantics clearer.
2. **Proposal-to-project handoff is two-step/manual.** Accepting a proposal sets the inquiry to Won; creating/attaching the project remains a separate owner action. Confirm whether this is desired control or a missed handoff. Do not auto-create projects without an explicit acceptance/rollback decision.
3. **Proposal actions remain a separate action type.** They already appear in the dashboard sales summary and source-labeled unified attention view, but remain stored separately from generic CRM follow-ups. Confirm whether current presentation and due-date semantics are sufficient while retaining proposal ownership and persistence.
4. **`components/dashboard/connected-operations.tsx` is unreferenced in the reviewed source tree.** It contains a legacy Hub CRM summary/API bridge and duplicate pipeline-value display; `rg` found no imports/usages. The active Hub flow is in Operations/Automation Hub components and attention adapters. Candidate for removal/archive after confirming no external dynamic import or branch-specific consumer.
5. **Navigation labels blur boundaries.** “CRM” spans inquiry management, consultations, and research discovery; “Insights” includes Marketing and Operations; Projects and Tasks are anchors rather than standalone routes. Navigation works, but the owner must know these relationships to infer where data lives.
6. **Client portal readiness is not customer activation.** The owner pages support access administration, publishing, preview, and readiness. Readiness spec keeps access/launch false absent approved gates. Treat the workflow as incomplete for live customer service until separately authorized release evidence exists; do not infer activation from the presence of pages/tables.
7. **Hub and Website CRM remain separate at identity level, with an active side-by-side queue.** `/dashboard/leads` displays Website inquiries and Hub CRM opportunities together through `LeadPriorityQueue`, but links Hub rows to the Hub pipeline and performs no identity matching or shared status write. The unreferenced `ConnectedOperations` component duplicates a Hub summary presentation; it is not the active integration.
8. **Production/system status is not one consolidated health record.** Operations observations are point-in-time and non-persistent, while Registry evidence is owner-recorded inventory/readiness. This is an explicit boundary, not a missing synchronization feature.
9. **Scheduled prospecting tools are outside the codebase.** Issue #119 names a scheduled ChatGPT prospecting queue and paused older app-prospect monitor, but neither is referenced in main source. Their current status, inputs, duplicate behavior, and owner are unverified. Keep outputs routed into existing Opportunity Discovery/CRM only; do not recreate either schedule or create a second prospect database as part of this audit.
10. **Quick Launch account targets need owner confirmation.** Workspace settings can override GitHub/Vercel targets; when unset, both fall back to `4twentydev`. The links are generated consistently, but saved settings and target ownership were not read from the owner workspace, so correctness is unverified; do not call them obsolete from the code alone.
11. **Calendar/task/briefing overlap is bounded and explicit.** Calendar/Google Tasks now enter the ordinary Dashboard through CC-021; briefing generation/playback and Vercel cron remain separate. Project tasks, Google Tasks, and GitHub issues/PRs are presented together but not reconciled by identity or copied into a common store. The current contracts describe unavailable/partial results rather than treating failures as empty data.
12. **Legacy specs/handoffs are not runtime features.** CC-018/020/021/027 and later CC-039/040 artifacts document successive implementations. Preserve verification/history; reconcile stale “active” claims against live main/PR state instead of deleting prior evidence. The live main includes merged PRs #113–#115, despite older handoff text recording earlier open/draft states.
13. **Two attention/briefing artifacts are unmounted.** `components/dashboard/connected-operations.tsx` has no in-repository import; `DashboardOperationsBriefing` is explicitly unmounted in CC-021 spec and has no current call site. Both are removal candidates after final static/dynamic consumer check. `LeadPriorityQueue` is active and must not be confused with the dead ConnectedOperations implementation.
14. **Specs 039/040 contain stale unchecked delivery tasks.** Their task lists still have unchecked “push/open draft PR” items, while live PRs #114 and #115 are merged and their code is on main. Verification records retain correct historical evidence; reconcile the task/active status in the next documentation closeout, preserving the evidence and original sequence.
